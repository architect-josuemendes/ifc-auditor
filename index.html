01 · Problem

Validation happens too late.

Most clash-detection and quality-control workflows run after the IFC file reaches the CDE. By then, finding that a discipline forgot to populate Pset_WallCommon.FireRating on 144 walls means another federation cycle, another coordination meeting, another week lost.

BIM Managers receive IFC deliverables from sub-consultants and need to verify compliance with the project's BEP and EIR before accepting the file. Manual inspection in a viewer is slow, error-prone, and produces no audit trail. The typical outcome: issues that could have been caught in five seconds get discovered in the next coordination meeting.

The fix is simple: move validation left. Run it on every consultant delivery. Return a clean HTML report with exactly what's missing. Send it back with actionable items before the file is even accepted into the CDE.

02 · How it works

Sixty seconds from IFC to report.

The full pipeline is two Python files, one YAML config, and one Jinja2 template. It's intentionally small — readable in 15 minutes, adaptable to any BEP in under an hour.

  1. Parse the IFC with ifcopenshell The model is loaded once. All checks operate on the in-memory representation — no viewer, no proprietary API, no cloud dependency. Runs offline.
  2. Evaluate rules from a YAML config Each rule specifies a check type, target class, property, severity, and parameters. Seven check types are built in: regex, schema, count_min, property_required, material_required, spatial_orphans, unique_guids. Adding a new type is ~15 lines.
  3. Classify failures by severity Every rule carries a severity level. Critical failures block CDE acceptance and produce exit code 1 — CI/CD-ready. Major failures require remediation before construction. Minor failures are logged as RFI-track items.
  4. Render a navigable HTML report The Jinja2 template produces a self-contained HTML file with per-rule pass/fail, coverage percentages, and a drill-down table of failing GlobalIDs and their reason codes. No dependencies required to open the report.
  5. Return the report before accepting the file Drop the tool into your delivery workflow. The consultant gets a machine-generated QA report within seconds of submission — not at the next federation meeting.
03 · Included rules

10 rules across 5 categories.

The shipped rules.yaml covers the most common BEP/EIR gaps encountered in multi-discipline coordination. Copy it and customize per project.

Rule ID What it checks Severity
naming_iso19650 ISO 19650 naming — IfcProject.Name matches Annex C pattern Major
schema_version Schema version — IFC schema is IFC4 or IFC4X3 Critical
storey_count Storey presence — at least one IfcBuildingStorey exists Critical
spatial_orphans Spatial assignment — all physical elements assigned to a spatial structure Major
wall_firerating Fire rating — all walls have Pset_WallCommon.FireRating Major
wall_loadbearing Load-bearing flag — all walls have Pset_WallCommon.LoadBearing Minor
door_isexternal Door classification — all doors have Pset_DoorCommon.IsExternal Major
wall_material Wall material — all walls have material assignment Major
slab_material Slab material — all slabs have material assignment Major
unique_guids GUID uniqueness — all GlobalIds are unique across the model Critical
Design note

Severity follows the same logic as coordination BCFs: critical blocks acceptance, major blocks construction sign-off, minor is RFI-tracked. The same three-tier model used across the ROCKOs coordination workflow.

04 · Live demo

Run it. Read the report.

The CLI produces a summary to stdout and a full navigable HTML report. Exit code is 0 if all critical rules pass, 1 otherwise — CI/CD drop-in.

# Clone and install
$ git clone https://github.com/architect-josuemendes/ifc-auditor.git && cd ifc-auditor
$ pip install -r requirements.txt

# Generate the synthetic test IFC (30 walls, 12 doors, intentional defects)
$ python generate_sample.py
✓ Synthetic IFC generated: examples/sample.ifc

# Run the audit
$ python audit.py examples/sample.ifc --rules rules.yaml --output report.html
▸ Loading examples/sample.ifc...
▸ 4/10 rules passed (40%)
  Critical failures: 0
  Major failures:    5
  Minor failures:    1
▸ Rendering report.html...
✓ Report written: report.html
Live audit report — sample.ifc · 4/10 rules passed Open full report ↗
What the report shows

Every rule produces a pass/fail verdict, a coverage percentage (passed elements / total checked), and a drill-down table of failing GlobalIDs with machine-readable reason codes. The report is fully self-contained — no server, no dependencies. Send it as an attachment, open it in any browser.

The 40% pass rate on the synthetic model is intentional: the test IFC ships with missing FireRating properties, orphaned elements, and non-compliant naming — exactly what a real consultant delivery might look like before QA.

06 · Tech stack

Small, readable, extensible.

Two Python files total. The entire pipeline — parsing, rule evaluation, report rendering — is under 400 lines. No proprietary dependencies. No cloud calls. Runs on any machine with Python 3.10.

To add a new check type: write one function (~15 lines) and add one entry to the CHECKS dict. To use it: add a rule block to your YAML. That's the full extension surface.

Python 3.10+ ifcopenshell 0.8+ click Jinja2 PyYAML IFC4 / IFC4X3 ISO 19650 HTML reports CI/CD-ready
CI / CD integration

The CLI exits with status 1 when any critical rule fails, making it drop-in for any CI pipeline. Add it as a gate on your model delivery step — the model only reaches the CDE if critical checks pass.

# .github/workflows/ifc-audit.yml
- run: pip install -r requirements.txt
- run: python audit.py models/architecture.ifc --rules bep.yaml
# exits 1 on any critical failure → blocks merge
07 · Context

The missing upstream gate for CS1.

The ROCKOs Caracas coordination project started with 340 critical clashes detected at first federation. A significant share of those clashes were traceable to upstream data quality issues: elements missing property assignments, orphaned geometry, inconsistent naming that broke automated clash filters.

IFC Auditor is the tool that should have run on every consultant delivery before federation. The 94% clash reduction achieved over 10 weeks was coordination work — but some of it was avoidable with a pre-acceptance gate. This tool closes that loop.

Both tools are now part of the same open-source coordination toolkit: ifc-auditor validates deliverables upstream; bim-clash-analytics tracks and resolves what slips through.
